## PR1 — order-aware chunk merge (UC-U38)

Fixes Codex P1 on #59: a one-sided chunk *reorder* was silently dropped, because
reassembly used base order and chunk vertices carried no ordering.

- `mergeChunkOrder(base,left,right []chunk, body)` three-way merges the chunk
  *key sequence*, recomputed from the ordered `Split` slices — decoupled from the
  content merge. Neither side reordered → base order + each side's additions
  (byte-identical to prior behavior, so existing UC-U36/UC-U37 tests are
  unaffected). Exactly one side reordered → its sequence is authority (preserving
  its reorder and its own additions' placement); other side's additions appended.
  Both reordered identically → accept; incompatibly → conflict (file-level).
- **Design catch (why the workflow paid off):** the first instinct — store an
  order index on each chunk vertex — is a correctness bug. `internal/revision`
  `vertexContentEqual` compares whole attribute maps, so an order attr turns an
  independent reorder into a false modify/modify conflict, and a dense index
  renumbers later siblings, manufacturing conflicts on unrelated edits. Order is
  therefore never stored on the vertex; it is recomputed at merge time.
- Doc fix (Copilot): the goChunker header said "Rename alignment"; corrected to
  "Move alignment" (a rename changes the symbol key, so it does not align — it is
  a delete+add; rename detection is not attempted). Also corrected the
  `chunkMerge` doc: `ok==false` now covers content conflict, order conflict, or
  gate failure.

Honest limit: the Go chunker splices a decl together with its trailing blank
line, so moving a decl to last changes its trailing whitespace; if that decl is
also edited on the other side it surfaces as a conflict rather than merging —
surfaced, never silently dropped. Reorders that keep each moved decl followed by
another decl merge cleanly (verified: swap B/C + edit A → clean, order kept).

Tests: unit `mergeChunkOrder` (identity/authority/reorder+add/incompatible/
identical/deletion); CLI reorder+disjoint-edit preserved. Full suite green under
-race. Docs: UC-U38; index + ledger (65/65).

## PR2 — import-aware chunking + import-name gate (UC-U39)

Fixes Codex P1 on #60 (import names absent from the gate) and the daily-annoyance
gap (two different added imports conflict).

- `goChunker.Split` decomposes a parenthesized `import (...)` into head / one
  chunk per spec (`import:<path>`) / tail. Distinct added specs become
  independent chunk additions the graph engine unions — no bespoke import
  differ. Single-line `import "x"` stays one chunk.
- `chunkmerge.go groupImportChunks` regroups decomposed import chunks (head,
  specs, tail) contiguously on reassembly — the generic order merge would append
  an added spec after the closing paren (invalid Go). Correction to the design
  synthesis, which assumed the generic path sufficed; it does not for
  add-spec-to-existing-block.
- Gate: `topLevelNames` IMPORT case now returns `importLocalNames` (alias, or
  `path.Base`; `_`/`.` skipped). Closes the P1: `import "fmt"` vs `var fmt`,
  duplicate imports, and same-alias clashes are refused.

Head-to-head: base imports fmt; A adds `os`+useOS, B adds `errors`+useErr,
main() untouched → git CONFLICTS, Got merges CLEAN with all three imports and
both funcs, valid Go. Byte-fidelity (Risk-2) covered by Split→Join round-trip
tests over grouped/aliased/blank/dot/empty/single-line/doc import shapes.

Honest limit: `path.Base` name heuristic is wrong for e.g. gopkg.in/yaml.v2; the
go/types gate (PR3/UC-U40) reads the real package name.

Tests: import round-trip, gate collisions, CLI union + collision-refused. Full
suite green under -race. Docs: UC-U39; index + ledger (66/66).
