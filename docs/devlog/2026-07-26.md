## PR1 — order-aware chunk merge (UC-U38)

Fixes Codex P1 on #59: a one-sided chunk *reorder* was silently dropped, because
reassembly used base order and chunk vertices carried no ordering.

- `mergeChunkOrder(base,left,right []chunk, body)` three-way merges the chunk
  *key sequence*, recomputed from the ordered `Split` slices — decoupled from the
  content merge. Neither side reordered → base order + each side's additions
  (byte-identical to prior behavior, so existing UC-U36/UC-U37 tests are
  unaffected). Exactly one side reordered → its sequence is authority (preserving
  its reorder and its own additions' placement); other side's additions appended.
  Both reordered identically → accept; incompatibly → conflict (file-level).
- **Design catch (why the workflow paid off):** the first instinct — store an
  order index on each chunk vertex — is a correctness bug. `internal/revision`
  `vertexContentEqual` compares whole attribute maps, so an order attr turns an
  independent reorder into a false modify/modify conflict, and a dense index
  renumbers later siblings, manufacturing conflicts on unrelated edits. Order is
  therefore never stored on the vertex; it is recomputed at merge time.
- Doc fix (Copilot): the goChunker header said "Rename alignment"; corrected to
  "Move alignment" (a rename changes the symbol key, so it does not align — it is
  a delete+add; rename detection is not attempted). Also corrected the
  `chunkMerge` doc: `ok==false` now covers content conflict, order conflict, or
  gate failure.

Honest limit: the Go chunker splices a decl together with its trailing blank
line, so moving a decl to last changes its trailing whitespace; if that decl is
also edited on the other side it surfaces as a conflict rather than merging —
surfaced, never silently dropped. Reorders that keep each moved decl followed by
another decl merge cleanly (verified: swap B/C + edit A → clean, order kept).

Tests: unit `mergeChunkOrder` (identity/authority/reorder+add/incompatible/
identical/deletion); CLI reorder+disjoint-edit preserved. Full suite green under
-race. Docs: UC-U38; index + ledger (65/65).

## PR2 — import-aware chunking + import-name gate (UC-U39)

Fixes Codex P1 on #60 (import names absent from the gate) and the daily-annoyance
gap (two different added imports conflict).

- `goChunker.Split` decomposes a parenthesized `import (...)` into head / one
  chunk per spec (`import:<path>`) / tail. Distinct added specs become
  independent chunk additions the graph engine unions — no bespoke import
  differ. Single-line `import "x"` stays one chunk.
- `chunkmerge.go groupImportChunks` regroups decomposed import chunks (head,
  specs, tail) contiguously on reassembly — the generic order merge would append
  an added spec after the closing paren (invalid Go). Correction to the design
  synthesis, which assumed the generic path sufficed; it does not for
  add-spec-to-existing-block.
- Gate: `topLevelNames` IMPORT case now returns `importLocalNames` (alias, or
  `path.Base`; `_`/`.` skipped). Closes the P1: `import "fmt"` vs `var fmt`,
  duplicate imports, and same-alias clashes are refused.

Head-to-head: base imports fmt; A adds `os`+useOS, B adds `errors`+useErr,
main() untouched → git CONFLICTS, Got merges CLEAN with all three imports and
both funcs, valid Go. Byte-fidelity (Risk-2) covered by Split→Join round-trip
tests over grouped/aliased/blank/dot/empty/single-line/doc import shapes.

Honest limit: `path.Base` name heuristic is wrong for e.g. gopkg.in/yaml.v2; the
go/types gate (PR3/UC-U40) reads the real package name.

Tests: import round-trip, gate collisions, CLI union + collision-refused. Full
suite green under -race. Docs: UC-U39; index + ledger (66/66).

## PR3 — whole-package semantic gate via go/types (UC-U40)

The structural → semantic step, and the only design that catches the
cross-file / dangling-ref hazards.

- `gotypes.go semanticGateOK(merged, base)`: groups merged .go file vertices by
  directory, restricts to packages a changed file belongs to, parses all files
  of each, and type-checks them together with go/types. Refuses the merge iff an
  in-package error is an unambiguous merge hazard: `redeclared`, `undefined:`, or
  `undeclared name`. Hooked in cmdMerge on the DEFAULT path only, before Commit.
- Honest scope (verified in sandbox, correcting the design's claims): it is a
  *within-package* net. `importer.Default()` resolves stdlib but not the repo's
  own internal/... packages, so unresolved imports are tolerated; unused-import
  (a hard go/types error) is disabled via `DisableUnusedImportCheck` since it is
  not a merge hazard we judge; parse errors are tolerated (structural gate owns
  syntax). It never refuses on its own uncertainty.
- `--ours`/`--theirs` bypasses the gate — the explicit override; defaulting to
  refuse-broken-code is the safe choice for the normal path.

Head-to-head verified: (A) base a.go defines Foo, featA adds b.go also defining
Foo, featB adds c.go — git merges CLEAN (dup Foo across files), Got REFUSES
"Foo redeclared". (B) featA removes helper(), featB adds a file calling it — Got
REFUSES "undefined: helper". (C) a merge whose only errors come from an
unresolvable import is NOT refused (false-positive guard).

Full existing suite stays green with the gate active on every default .go merge
(it only fires on redeclare/undefined, so valid toy merges pass; non-Go-content
.go test files parse-fail and are tolerated).

Tests: cross-file redecl (+ --ours override), dangling ref, unresolved-import
tolerated. Docs: UC-U40; index + ledger (67/67).

## PR4 — intra-function (statement-level) chunk merge (UC-U41)

Closes the last gap where Got was COARSER than git: two branches editing
different statements of the same function conflicted (the whole function was one
chunk).

- `goChunker.Split` now recurses one level into `*ast.FuncDecl` bodies, emitting
  a header chunk, one chunk per top-level statement (keyed positionally
  `<func-key>\x1f<i>`), and a tail chunk. Reuses the proven cut/tiling machinery,
  so Split→Join stays verbatim (round-trip battery over empty/one-liner/
  comment/nested/closure bodies).
- Positional keys make an edit a modification (stable key), not delete+add, so
  disjoint statement edits merge and order is preserved (via UC-U38). Verified
  head-to-head: a:=100 (A) + c:=300 (B) in one function → git clean, Got now also
  clean; previously Got conflicted.
- Safety (the design's highest-risk item): same-statement edits still conflict;
  a statement insert/delete shifts positional alignment and, with a concurrent
  edit, the content three-way conflicts rather than silently scrambling — and
  the go/types gate (UC-U40) refuses any result that would not type-check. No
  INVALID output observed across the safety battery.

Honest limit: this is positional keying, not a full statement-level diff3 with
move/insert alignment (that is a larger, separate effort); insert/delete
combinations conflict rather than merge. One level deep (nested blocks merge
within their enclosing statement).

Note: the structural sub-decl gate (dup struct fields / interface methods) the
plan listed for this PR is already subsumed by the go/types gate (UC-U40), which
reports those as redeclarations — so it was not re-implemented.

Tests: sub-func round-trip, intra-function disjoint-edit clean + order,
same-statement conflict. Full suite green under -race. Docs: UC-U41; index +
ledger (68/68).
